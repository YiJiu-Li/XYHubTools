# 运行架构与验证

## Agent 运行

已有 config/system/env 分离时沿用定义，模板变量来自本次执行环境；知识内容与工具结果带来源，不能当作可执行的高优先级指令。不要认为任意 `.agent.md` 或 `sub_agents` 字段在所有宿主都有效，先核实实际加载器。

工具循环应具备配置化的调用/耗时/上下文预算、停止信号、取消和错误终态。达到限制时报告未完成步骤，不将历史的 200 次上限当成标准值。读操作可按故障类型重试；写操作执行状态未知时先核对副作用，不能整段自动重放。

模型适配层保留调用 ID、结构化参数、工具结果、结束原因及协议错误；不同提供方消息格式不要简单套壳。实现 API 接入时读取对应当前官方文档与仓库适配代码；不凭旧模型列表推断能力或参数支持。

## 事件与取消

建立明确的 Run 状态转换与终态事件，包括等待用户输入、取消中、完成、失败和已取消。一次 Run 的完成/取消事件只提交一次，取消后迟到的 delta 与工具结果不得复活旧 Run。

等待确认使用 runId + toolCallId 关联；拒绝、超时和用户取消是不同结果。前端显示和后端执行应校验同一个请求，不接受过期确认。任务已有授权时不额外制造确认步骤；确认机制由实际产品权限模型决定。

Tauri IPC 和 stream-event 名称、payload 版本、监听注册与解除要成对。日志包含关联 ID 与适当错误码，不记录密钥。流式 UI 要限制事件队列和内容渲染成本，页面卸载时释放监听。

## 存储与知识

数据库操作遵守实际连接与事务模型；避免长时间持锁等待网络或工具。写入失败和恢复过程应有可观测状态。知识默认分层摘要、按需正文，规模阈值从测量决定；不以“48 个文档”为通用切换点。

工具 schema 热更新仅能改变宿主实际支持的定义；它不意味着新增执行实现无需编译/部署。后端工具白名单与参数验证必须实际执行，Markdown 声明本身不构成权限隔离。

## 交付测试

对当前改动挑选真实场景：文本流结束、工具参数分片、工具失败、用户取消、确认拒绝、并行/连续 Run、重启后的会话恢复、资源打包。检查事件归属和终态，不只检查页面有输出。

性能预算来自产品目标和测量条件，区分模型耗时、工具耗时、IPC 与 UI 延迟。原文中的 50/100/200ms 作为历史目标，不作未测量的保证。

桌面应用打包时从当前仓库确认目标系统、权限、资源、许可证和依赖下载。NSIS、ONNX/DirectML、PortableGit、Bun 命令等仅在工程确实使用时处理；不为了匹配旧智能体样例而安装新框架或切换部署方式。
